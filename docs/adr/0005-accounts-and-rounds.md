# ADR 0005: 회원·가상 계좌·일일 라운드

- 상태: 채택 (2026-11-25, 사용자 결정: 모의투자 서비스, 이메일+비밀번호, 매일 새 라운드, SQLite)
- 범위: `dev/service` 브랜치. 발표 버전(`presentation-v1`)과 공개 서버는 발표가 끝날 때까지 바꾸지 않는다.

## 결정
1. **회원**: 이메일+비밀번호. ASP.NET Core Identity Core(사용자·비밀번호 해시·잠금) + EF Core SQLite. 세션은 HttpOnly·Secure·SameSite=Lax 쿠키. 상태를 바꾸는 요청은 Antiforgery 토큰 헤더 필수. Data Protection 키는 볼륨(`/data/keys`)에 저장해 재시작 후에도 로그인이 유지된다. 이메일 인증·비밀번호 찾기는 메일 발송 설정이 필요해 이번 범위에서 뺀다.
2. **주문 소유권**: 주문 명령의 기존 `AccountId` 칸에 사용자 ID를 넣는다(봇은 `bot:이름`). 저널 형식은 바뀌지 않는다. 로그인하지 않으면 시세·실험만 볼 수 있고 주문할 수 없다. 남의 주문 조회·취소는 404(존재 여부를 숨긴다).
3. **가상 계좌(라운드)**: 시장 세대(매일 05:00 초기화) = 라운드. 사용자는 라운드마다 현금 10,000,000원 + HOGA 1,000주로 시작한다(임의 지정). 매수는 `가격×수량`만큼 현금을, 매도는 수량만큼 주식을 묶고(hold), 체결 시 정산, 취소·초기화 시 해제한다. 잔고 부족은 서버 규칙 거부(`InsufficientCash`/`InsufficientShares`, KRX 규칙 아님, 저널에 기록하지 않음).
4. **결정성**: 계좌 원장은 저널(명령)과 엔진 이벤트로 다시 만드는 투영이다. 재시작·crash 복구 시 저널 재생으로 같은 잔고가 나와야 한다(상태 해시에 원장 해시를 함께 보고). 잔고 검사는 처리 루프 안에서 저널 기록 전에 한다.
5. **SQLite**: 사용자(Identity 테이블), 라운드 결과 보관(라운드별 최종 순위·수익률), 로그인 감사 기록만 둔다. 실시간 계좌는 메모리 투영. 초기화 시 라운드 결과를 SQLite에 저장하고 백업한다.
6. **랭킹**: 수익률 = (현금 + 보유주식×최근 체결가) ÷ 시작 평가액 − 1, 만분율 정수(bp). 현재 라운드는 처리 루프가 10초마다(임의 지정) 계산한 스냅샷을 제공한다. 닉네임만 공개하고 이메일은 공개하지 않는다.
7. **관리자**: `Admin` 역할 계정(서버 CLI로 생성). 관리자 키 헤더(`X-Admin-Key`)는 운영 스크립트용으로 유지한다.

## 대안과 단점
- PostgreSQL: 면접에서 자연스럽지만 공개 서버 메모리 60~100MB 추가. SQLite는 동시 쓰기 한계가 있으나 쓰기는 가입·로그인·라운드 종료뿐이다.
- 계좌를 DB에 실시간 기록: 체결마다 DB 쓰기가 생기고 저널과 두 진실 원천이 된다. 투영 방식은 재생 비용이 저널 길이에 비례한다(매일 초기화로 상한).
- 단점: 라운드가 매일 끝나 장기 투자 경험이 없다. 이메일 인증이 없어 가짜 이메일로 가입할 수 있다(요청 제한과 가입 제한으로 완화).
