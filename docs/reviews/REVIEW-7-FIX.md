# REVIEW-7 배포 전 수정

기준: `7c2c493`, 브랜치 `fix/REVIEW-7`. 엔진 규칙, 실험 수치, 계약 버전(v0.4)은 유지했다.

| 항목 | 원인과 수정 | 검증 |
|---|---|---|
| 1. 장 간 주문 ID (7A P1-1 / 7B HIGH) | 순번이 리셋되어 ID가 재사용되었다. 새 장의 GUID를 저널 헤더에 기록하고 REST·봇이 같은 접두를 사용한다. 세대 필드가 없는 저널은 첫 초기화까지 레거시 ID 규칙으로 복구한다. 보관 기한 경과 판단도 활성 장 ID만 검사한다. 계약에 ID 불투명성을 한 줄 추가했다. | 새 장의 같은 순번 ID가 다르고, 새 주문이 존재해도 이전 ID의 조회·취소가 404임을 검증. 실제 테스트 호스트 재시작 뒤 동일 세대의 후속 ID, 이전 주문 설명 및 상태 해시 검증. 기존 저널 테스트 통과. |
| 2. 초기화 파일 이동 실패 (7A P1-2) | writer를 닫은 뒤 이름 변경에 실패하면 예외가 시장 루프를 종료했다. 이동 I/O 오류에 경고를 남기고 원본과 순번을 확인해 writer를 다시 연다. 관리자 호출은 503, 정기는 5분 후 재시도(임의 지정). 원본을 다시 쓸 수 없으면 정합성을 위해 중단한다. | 대상 이름에 디렉터리를 만들어 이동을 실패시켰다. 이전 상태·주문 설명 유지, 후속 주문 기록 및 장애 제거 뒤 초기화 성공을 검증. |
| 3. Compose 자원 한도 (7A P1-3) | swap·CPU·로그 한도가 없었다. 메모리와 swap 포함 한도를 모두 192MiB, CPU 0.5개, `json-file` 로그 10MiB × 3파일로 제한했다(임의 지정). | 로컬 `docker compose config --quiet` 통과. 실제 호스트에서 자원 경쟁은 미측정. |
| 4. 요청 제한 (7A P1-6) | 공개 쓰기와 관리자 인증 시도에 제한이 없었다. ASP.NET Core 내장 고정창으로 IP별 주문·취소 합산 20건/초, 관리자 API 합산 10건/분(임의 지정). 설정한 사설 Docker IPv4 CIDR에서 온 X-Forwarded-For 한 홉만 신뢰한다. 봇은 내부 큐 그대로이며 초과 HTTP 429와 화면 문구를 추가했다. | 주문/취소 한도 공유, 일반 조회·관리자 분리, 429 JSON, 외부 IP 헤더 무시, 신뢰 CIDR의 바로 앞 홉 및 IP별 분리, 화면 한국어 메시지 검증. |
| 5. 배포 스크립트 (7A P1-5 / 7B MEDIUM) | dirty 트리 내용이 커밋 태그를 달 수 있었고 이전 서버 헬스에 의존했으며 게시 산출물 누락을 걸러내지 않았다. `-AllowDirty`만 우회 가능하며, 실배포 모드는 `-HealthUrl` 필수, `summary.json` 누락은 패키징 전 중단한다. | PowerShell 파싱, dirty 기본 거절, `-AllowDirty` 통과 후 게시 스텁의 `summary.json` 누락 거절, 헬스 URL 미지정 차단을 로컬 검증. |
| 6. 실험 그래프 (7B MEDIUM) | 0ms 극값의 시작 기준가가 실제 체결 점으로 표시되었다. 데이터에서 0ms 체결을 구분할 수 없으므로 0ms는 마름모와 `시작 기준가` 범례, 양의 시각은 실제 체결 점으로 표시한다. | 한쪽 극값만 0ms인 픽스처에서 마름모와 별도 체결 점 검증. 비0ms 극값의 좌표 검증 유지. |
| 7. 초기화 신호 유실 (7B MEDIUM) | 재연결은 시세 이력만 비워 내 주문이 남았다. 이전 호가 순번보다 재연결 첫 `bookSnapshot`의 순번이 작으면 내 주문·체결·봉을 비운다. | 초기화 알림 없이도 첫 스냅샷 순번이 하락하면 세 목록이 비는 테스트. 순번이 증가하는 정상 재연결과 명시적 초기화 회귀 테스트 유지. |
