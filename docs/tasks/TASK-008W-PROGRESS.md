# TASK-008W 진행 기록

## 구현

- `Comparison`은 계약 v0.3의 `demo`를 조회한다. 목은 `demo`와 `exp-FatFinger-16`을 시드 16의 목 실험으로 반환한다. 시드 16은 `docs/experiments/SUMMARY.md`의 선정 결과이며 임의 지정한 값이 아니다. 기존 목 전용 `exp-1`과 기존 테스트는 유지했다. 서버 모드의 시나리오 호출과 관리자 키 입력·`sessionStorage` 경로는 기존대로 두었다.
- SignalR 최초 연결·재연결 때 `syncing`에 진입하면서 체결과 봉을 한 번 비운다. SignalR 연결 알림보다 이력 메시지가 먼저 오면 그 메시지를 적용하기 전에 비운다. 연결 성공만으로 완료 표시하지 않고 첫 `bookSnapshot`을 적용한 뒤 연결됨으로 전환한다. 최근 체결 최대 50건(계약에서 임의 지정)은 스크롤 목록에 최신순으로 표시한다. 오늘의 봉은 시작 시각 기준으로 갱신하고 정렬해 모두 표시한다. 목 화면의 기존 체결 6건·봉 60개 표시 범위는 유지했다.
- **주문 상태: 설명 API 폴링을 선택했다.** 계약의 `trade`에는 주문 ID가 없고 `bookSnapshot`은 가격대별 집계라, 특히 같은 가격에 여러 주문이 있을 때 개별 체결·취소를 판정할 수 없다. `GET /api/orders/{id}/explanation`의 상태를 목록과 설명 패널에 함께 반영한다.
  - **임의 지정:** 브라우저 화면 인스턴스당 2초에 최대 1건 자동 조회. 직접 조회를 포함해 다른 설명 요청이 진행 중이면 이번 자동 조회를 건너뛴다. 상태 미확인 또는 미종료인 내 주문만 순환하므로 활성 주문이 많으면 주문별 갱신은 그만큼 늦어진다. 첫 스냅샷 도착 전이나 재연결 중에는 자동 조회하지 않는다.
  - 접수 직후 및 필요 시 직접 선택·취소 시 즉시 조회하며, 같은 ID의 조회는 중복 요청하지 않는다. 대기·단일가 대기·부분 체결에만 취소 버튼을 보이고, 완료·취소·거부 상태는 자동 조회에서도 제외한다. 취소 성공은 즉시 반영하고 늦게 도착한 취소 전 조회로 되돌리지 않는다.
  - 404만으로 체결·취소·거부를 추정할 수 없어 `상태 확인 불가`를 표시하고 자동 조회 대상에서 제외한다. 일시적인 요청 오류는 조회 실패로 표시하되 종결로 처리하지 않는다. 접수 단계 거부는 주문 ID가 없으므로 종전처럼 목록에 추가하지 않고 거부 사유를 표시한다.
- 수량은 `1~1,000,000`의 정수만 전송한다. 상한은 CONTRACT v0.3 `Market:MaxOrderQuantity` 기본값(서버에서 임의 지정한 입력 한도)과 같다. KRX 규칙이 아니다. 새 의존성이나 계약 변경은 없다.

## 검증

- Windows PowerShell 7 / Node 26.5.0. `web/`에서 각 셸에 `npm_config_script_shell`과 `NODE_OPTIONS=--no-experimental-webstorage`를 지정했다. 첫 설치 시 PowerShell 가상 경로가 npm 캐시 경로에 포함되어 실패한 뒤, 실제 `web/.npm-cache/` 경로로 수정해 `npm ci`를 완료했다(291개 패키지).
- `npm run lint`: 경고·오류 0. `npm run test -- --run`: **5파일, 47개 통과**(기존 32개 + 신규 15개). `npm run build`: 타입 검사 및 70모듈 번들 성공. 기존 SignalR 내부 주석을 Rollup이 제거한다는 경고 2개만 발생했다.
- 가짜 허브/REST와 목 모드에서 이력 초기화 순서, `demo`, 종료 상태와 취소 버튼, 비선택 주문 폴링 및 재연결 중 중지, 수량 양끝과 범위 밖을 확인했다.
- **미검증:** 병렬 작업 중인 008S 실제 서버와의 통합(시나리오, 실험 조회, 이력 재전송·재연결, 주문 상태). 개발 서버는 실행하지 않았다. push 없음.

## 제안

- 활성 내 주문이 많아지거나 사용자 수가 늘어나면, 인증된 내 주문 상태 이벤트를 계약에 추가하는 방안을 검토한다. 폴링 부하와 갱신 지연을 줄일 수 있지만, 주문 소유권 확인과 재연결 시 상태 보강이 필요하다. 이번에는 구현하지 않았다.
